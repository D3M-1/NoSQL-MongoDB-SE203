الشرح النظري والمفاهيم الهندسية الأساسية الموسعة

📌 1. قيود قواعد البيانات العلائقية (Relational / SQL) وأسباب ظهور NoSQL:

ظهرت قواعد بيانات NoSQL كضرورة هندسية لمعالجة 3 قيود رئيسية أعجزت قواعد البيانات العلائقية التقليدية (RDBMS):

  • جمود الهيكل (Rigid Schema): تتطلب الجداول التقليدية معرفة مسبقة وثابتة لجميع الحقول وأنواعها قبل إدخال أي بيان. إذا طرأ تغيير على طبيعة التطبيق (مثل إضافة بريد إلكتروني إضافي أو رقم هاتف ثانٍ)، فإن كلفة تعديل الجداول برمجياً تكون باهظة ومحفوفة بالأخطاء، وتستلزم إعادة كتابة كود النظام وإجراء Database Migrations معقدة قد تعطل الخدمة.
  • معضلة فيضان القيم الفارغة (Null Values Flood): عند إضافة أعمدة جديدة لا يستخدمها سوى شريحة صغيرة من العملاء، تظل تلك الحقول محجوزة بقيم null لدى باقي ملايين المستخدمين، مما يؤدي إلى هدر ضخم في الذاكرة والمساحة التخزينية بلا طائل مع تدهور أداء قراءة القرص.
  • محدودية التوسع الرأسي (Vertical Scaling Limits): تعتمد قواعد البيانات العلائقية على التوسع الرأسي (Vertical Scaling / Scale Up) عبر ترقية مواصفات السيرفر الفردي (شراء معالج أقوى، ورام أعلى، وقرص أسرع)، وهذا له سقف فيزيائي وتكلفة مالية تتصاعد أُسياً. بينما تعجز عن التوسع الأفقي (Horizontal Scaling / Scale Out) والتوزيع السلس على آلاف السيرفرات المتزامنة منخفضة التكلفة لاستيعاب ملايين الطلبات في الثانية الواحدة (مثل أنظمة شركات آبل وأمازون وجوجل).
💡 جوهر NoSQL والـ Schema-less:

كلمة NoSQL تعني بالأساس Non-relational أو Schema-less؛ حيث يتميز هذا النموذج بأن كل مستند (Document) داخل نفس المجموعة (Collection) يمكن أن يحمل حقولاً مختلفة كلياً عن المستند المجاور له دون قيود أو إجبار، وتستطيع التطبيقات تطوير هياكل بياناتها ديناميكياً.

📌 2. الأنواع الأربعة الرئيسية لقواعد بيانات NoSQL:

  1. Key-Value (مفتاح - قيمة): مثل Redis و DynamoDB؛ تعتمد على ثنائية مفتاح وقيمة فائقة السرعة، ولكنها محدودة في الاستعلامات المعقدة.
  2. Wide-Columns (عائلات الأعمدة): مثل Cassandra و HBase؛ تخزن البيانات في مجموعات أعمدة وتصلح للملفات الضخمة وتحليلات السجلات.
  3. Graph (الشبكات والرسوم البيانية): مثل Neo4j؛ تعتمد على العقد والعلاقات (Nodes & Edges) وتصلح للشبكات الاجتماعية وأنظمة التوصيات.
  4. Document (المستندات): مثل MongoDB و CouchDB؛ تعتمد على تخزين البيانات في هيئة مستندات شبه مهيكلة (JSON/BSON)، وهو النمط الذي يجمع بين المرونة العالية والقدرة على الاستعلام المتقدم.

📌 3. معمارية التوزيع ومشاكل الفحص (Distribution & Search Dilemma):

  • كيفية التوزيع: عند تخزين المستند، يتم أخذ المفتاح الأساسي (Key) وتحويله إلى قيمة رقمية عبر دالة تقطيع وتمريره على دالة تجزئة وباقي قسمة (Hash Function / Modulo: Server_ID = Hash(Key) % Number_Of_Servers)؛ مما يحدد السيرفر الحاضن للمستند في زمن قياسي O(1).
  • المشكلة الهندسية (The Sequential Scan Dilemma): عند الاسترجاع بالبحث بقيمة غير المفتاح الأساسي (مثل البحث باسم موظف أو براتب أكبر من 10000)، يعجز النظام عن توظيف دالة التجزئة مباشرة؛ مما يجبر السيرفرات على إجراء فحص خطي متسلسل (Sequential Search / Collection Scan) للمرور على ملايين المستندات واحداً تلو الآخر لغياب الوصول العشوائي المباشر (Random Access)، مسبباً بطئاً كارثياً.
  • الحل الهندسي: إنشاء فهارس مخصصة في الذاكرة (In-Memory B-Tree Indexing) ترتب الحقول وتوجه المؤشرات (Pointers) نحو مواقع المستندات على القرص الصلب فوراً.
🧠 لمسة الخبير المهنية (Expert Architecture Note):

في الأنظمة الموزعة لـ MongoDB (Sharding)، يتم تقسيم البيانات أفقياً عبر مجموعات خوادم تسمى Shards بالاعتماد على ما يسمى Shard Key، وتوفر بنية الكلاستر وصولاً عالي التوفر (High Availability) من خلال مجموعات النسخ المتطابقة (Replica Sets) التي تحافظ على استمرارية العمل في حال تعطل أي خادم رئيسي.

📌 4. خريطة المصطلحات المقابلة (Mapping Terminology):

قواعد البيانات العلائقية (Relational SQL) قواعد بيانات مونجو (MongoDB) الدلالة الهندسية والوظيفية
Table (الجدول) Collection (الكولكشن) وعاء لتجميع المستندات ذات الصلة (بدون هيكل مجبر)
Row / Record (الصف / السجل) Document (المستند) وحدة البيانات الأساسية (كائن JSON/BSON مستقل ذاتياً)

Database Instance Cluster (الكلاستر) مجموعة كاملة من قواعد البيانات (Set of Databases) ضمن بنية الخوادم
Primary Key _id (ObjectId) معرّف فريد افتراضي 12-byte لكل مستند

📌 5. أدوات بيئة العمل والمطور (Developer Tools):

  • MongoDB Atlas: خدمة سحابية مدارة بالكامل (Database as a Service) بواجهة ويب (Web-based GUI)، وتمنح في خطتها المجانية (Shared Cluster M0) سعة 512 MB.
  • MongoDB Compass: تطبيق مكتبي ذو واجهة رسومية (Desktop GUI) يُثبت محلياً للاتصال بالسيرفرات وإدارة المستندات بصرياً وتحليل خطط تنفيذ الفهارس والاستعلامات.
  • VS Code + MongoDB Extension: إضافة برمجية تمكن المطور من إدارة القواعد والاتصالات، وكتابة الأكواد واستعراض النتائج تفاعلياً عبر ملفات Playground بصيغة .mongodb.

الإجابة النموذجية وتعليل الدكتور:

  1. الجمود الهيكلي (Rigid Schema): إلزامية تعريف كافة الأعمدة مسبقاً، وصعوبة وتكلفة تعديل الجدول لاحقاً عند تغير متطلبات العمل (تعديل كود النظام والتطبيق).

⚠️ مصيدة الامتحان 1: خطأ القوسين الزاويتين < > في الـ Connection String

عند نسخ رابط الاتصال من لوحة تحكم MongoDB Atlas، يظهر القالب الافتراضي هكذا: <password>.

الخطأ الشائع لدى الطلاب: استبدال كلمة password فقط مع إبقاء القوسين الزاويتين! فيكتب الطالب: mongodb+srv://admin:<mypassword>@cluster0.... يفسر السيرفر القوسين كحرفين فعليين داخل كلمة المرور، فيفشل الاتصال فوراً وتظهر رسالة Authentication Failed (Bad Credentials).

التصحيح المعتمد: حذف القوسين تماماً وكتابة الباسورد مجردة: mongodb+srv://admin:mypassword@cluster0...

⚠️ مصيدة الامتحان 2: الخلط بين الـ Schema-less وغياب تصميم البيانات

الخطأ الفكري الشائع: يعتقد بعض الطلاب أن كون MongoDB مرنة وخالية من المخطط الصارم (Schema-less) يعني أنه لا توجد قواعد تصميم، فيقومون بتخزين بيانات عشوائية تماماً بلا حقول مشتركة.

تعليق وتأكيد الدكتور: كلمة Schema-less تعني المرونة الهندسية على مستوى محرك قاعدة البيانات (Database Engine Flexibility)، بحيث لا يجبرك على أعمدة موحدة. ولكن على مستوى كود التطبيق (Application Layer)، يجب أن يكون هناك نمط مدروس (Schema Design) لضمان قدرة كود الواجهة والـ API على قراءة البيانات بدون أخطاء Undefined Property.

⚠️ مصيدة الامتحان 3: كارثة الفحص الخطي (Sequential Scan) عند غياب الـ Index

سؤال الامتحان الشهير: "إذا كان لدينا كلاستر NoSQL موزع على 10 سيرفرات ويحوي 10 ملايين مستند، كيف يسترجع مستنداً برقم SSN (غير المفتاح الأساسي)؟"

الجواب الحاسم: بما أن البحث لا يعتمد على المفتاح الأساسي (Key) المستخدم في دالة الـ Hash والـ Modulo، فإن السيرفرات تعجز عن توجيه الاستعلام إلى سيرفر محدد بزمن O(1)، فتضطر كافة السيرفرات لإجراء فحص خطي متسلسل (Sequential Scan) على ملايين المستندات واحداً تلو الآخر، مسببة تدهوراً كارثياً في الأداء وزمن الاستجابة. والحل الوحيد هو إنشاء فهرس B-Tree في الذاكرة.

الشرح النظري والمفاهيم الهندسية الأساسية الموسعة

📌 1. المواصفة القياسية العالمية لـ JSON (JavaScript Object Notation):

يعد JSON المعيار القياسي لتبادل البيانات وتخزينها في MongoDB (في صيغته الثنائية BSON). وتفرض المواصفة شروطاً صارمة لا تقبل التهاون:

  • إلزامية علامتي التنصيص المزدوجتين (Double Quotes Only): يجب أن تُحاط كافة المفاتيح (Keys) والنصوص (Strings) بعلامتي تنصيص مزدوجتين حصراً: "key": "value". يُمنع منعاً باتاً استخدام علامات التنصيص الفردية 'key' في الـ JSON القياسي، كما يُمنع ترك المفتاح مجرداً بدون تنصيص.
  • حساسية تامة لحالة الأحرف (Case Sensitivity): المفتاح "name" يختلف جذرياً في الذاكرة عن "Name" أو "NAME"، وتعتبر كحقول منفصلة تماماً.
  • الأنواع البيانية الستة المدعومة قياسياً (Standard JSON Types):
    1. Strings (النصوص): محاطة بدبل كوتيشن حصراً "Ali".
    2. Numbers (الأرقام): صحيحة أو عشرية مجردة 25 أو 9500.50.
    3. Booleans (القيم المنطقية): تكتب بحروف صغيرة ومجردة تماماً: true أو false (وليس True بحرف كبير ولا "true" كنص).
    4. Null (القيمة الفارغة المنعدمة): تكتب بحروف صغيرة ومجردة null.
    5. Arrays (المصفوفات والقوائم): محاطة بأقواس مربعة [ "item1", "item2" ].
    6. Objects (الكائنات المتداخلة): محاطة بأقواس معقوفة { "city": "Cairo", "zip": 12345 }.

الشرح النظري والمفاهيم الهندسية الأساسية الموسعة

📌 1. التبديل وإنشاء قواعد البيانات والكولكشنز (use & Implicit Creation):

  • الأمر use(<dbname>): يقوم بتحديد قاعدة البيانات النشطة للعمليات التالية، ويسند كائنها فورياً إلى المتغير المرجعي التلقائي db.
  • السلوك الضمني الفريد (Implicit Collection Creation): في MongoDB، إذا قمت بالإدراج في كولكشن غير موجود مسبقاً، فإن المحرك لا يطلق خطأ، بل يقوم بإنشاء الكولكشن وقاعدة البيانات على القرص الصلب فوراً وبشكل تلقائي عند أول عملية كتابة.
  • الأمر الصريح db.createCollection(name): يُستخدم عند الرغبة في إنشاء كولكشن مسبقاً، أو عند ضبط خيارات هندسية متقدمة (مثل تحديد حجم أقصى Capped Collections).

📌 2. المفتاح الأساسي _id وطبيعته في MongoDB:

  • الإلزامية والفرادة: كل مستند داخل أي كولكشن في MongoDB يجب أن يحمل حقلاً أساسياً يسمى حصراً _id (بحروف صغيرة وبداية بشرطة سفلية). ولا يمكن أن يتكرر هذا المعرف داخل نفس الكولكشن إطلاقاً.
  • التوليد التلقائي (Automatic ObjectId): إذا لم يمرر المطور قيمة للـ _id أثناء الإدراج، يقوم الخادم بتوليد معرّف فريد تلقائياً من نوع ObjectId (حجمه 12-byte، مشفر بنظام ست عشري 24-hex characters، ويحتوي على بصمة زمنية Timestamp، ومعرف الآلة Machine ID، ومعرف العملية Process ID، وعداد تسلسلي Counter).
  • التعيين اليدوي (Manual Override): يحق للمطور تمرير قيمة مخصصة للـ _id (مثل رقم صحيح أو كود نصي). فإذا حاول إدراج قيمة مكررة موجودة مسبقاً، يرفض النظام العملية فوراً ويطلق خطأ Duplicate Key Error (E11000).

📌 3. التعديل الأساسي: الفرق بين الإضافة/التحديث والحذف التام للحقول:

  • المعامل $set: يستقبل كائناً بالحقول المراد إضافتها أو تعديلها. إذا كان الحقل موجوداً تم تحديث قيمته، وإذا لم يكن موجوداً أضيف الحقل فوراً دون المساس ببقية حقول المستند.
  • المعامل $unset: يستقبل كائناً بأسماء الحقول المراد إزالتها. يقوم المعامل بحذف الحقل بالكامل مع اسمه وقيمته ومحوه من هيكل المستند، والقيمة المكتوبة أمامه شكلية (تكتب عادة "" أو 1).
🧠 تصدير البيانات من MongoDB Compass (JSON vs CSV):

عند تصدير بيانات الكولكشن عبر واجهة MongoDB Compass، هناك فارق هندسي جوهري بين الصيغتين:

  • صيغة JSON: تحافظ تماماً على الهيكل الكامل للبيانات بتفاصيلها وتداخلاتها المعقدة (Nested Objects & Arrays) وتحافظ على دقة أنواع الحقول، وهي الصيغة المثالية للنسخ الاحتياطي وإعادة الاستيراد.
  • صيغة CSV: تفقد العديد من أنواع البيانات والتفاصيل المتداخلة؛ نظراً لكونها تعتمد على تمثيل مسطح ثنائي الأبعاد (صفوف وأعمدة ثابتة) لا يستوعب المصفوفات والكائنات الفرعية.

⚠️ مصيدة الامتحان 1: نسيان الفلتر الفارغ {} في updateMany

إذا أردت تعديل جميع المستندات فكتبت: db.sales.updateMany({ $set: { status: "active" } }):

الخطأ الفادح: دالة updateMany تتطلب وسيطين إجبارياً: الأول هو الفلتر والثاني هو كائن التعديل. إذا مررت كائن $set كوسيط أول، فسيفشل الاستعلام ويرفض المحرك تنفيذه معلناً Invalid filter parameter. الصواب الحتمي وضع الفلتر الفارغ كوسيط أول: db.sales.updateMany({}, { $set: { status: "active" } }).

⚠️ مصيدة الامتحان 2: فخ الاستبدال التام وضياع الحقول (Full Replacement Trap)

تحذير الدكتور الصارم: في إصدارات السيرفر السابقة، إذا كتب المطور db.sales.updateOne({ _id: 1 }, { price: 25 }) بدون استخدام المعامل $set، فإن مونجو تمحو المستند بالكامل وتستبدله بمستند لا يحوي سوى _id وحقل price: 25 فقط! وتفقد الشركة الاسم والكمية وتاريخ الشراء نهائياً. لذلك استخدام $set إلزامي للحفاظ على البيانات القديمة.

الجواب الخاطئ: تصبح قيمة الإيميل نصاً فارغاً "" أو تصبح null.

الجواب الصحيح والدقيق: يتم حذف حقل email نهائياً من الذاكرة والقرص، وتصبح النتيجة وكأن الحقل لم يُخلق أبداً في ذلك المستند.

⚠️ مصيدة الامتحان 4: حصانة المفتاح الأساسي (Immutability of _id)

حقل _id محصن ومعصوم من أي تعديل (Immutable) بعد إنشائه. وإذا حاولت كتابة db.sales.updateOne({ _id: 10 }, { $set: { _id: 20 } })، يرفض السيرفر فوراً ويطلق استثناء: Performing an update on the path '_id' would modify the immutable field '_id'. وإذا كان لا بد من تغيير المعرف، يجب نسخ المستند بالمعرف الجديد وحذف القديم.

الشرح النظري والمفاهيم الهندسية الأساسية الموسعة

📌 1. الهندسة المعمارية للفهارس في MongoDB (In-Memory B-Trees):

  • الغاية الجوهرية: الفهرس (Index) هو هيكل بيانات شجري خاص (B-Tree) يُبنى ويُحفظ في ذاكرة الوصول العشوائي (RAM)، ويحوي نسخاً مرتبة من حقول معينة مع مؤشرات (Pointers) مباشرة نحو الموقع الفعلي للمستند على القرص الصلب. وبدونه، يضطر المحرك للقيام بـ Collection Scan فاحصاً ملايين المستندات واحداً تلو الآخر.
  • معنى الترتيب (Sort Direction 1 vs -1):
    • 1: فهرسة تصاعدية (Ascending) من الأصغر إلى الأكبر أو أ-ي.
    • -1: فهرسة تنازلية (Descending) من الأكبر إلى الأصغر أو ي-أ.
    • في الفهارس الفردية، لا يهم الاتجاه لأن المحرك يستطيع التجول في الشجرة في الاتجاهين. ولكن في الفهارس المركبة، فإن اتجاه الفهرسة يحدد بدقة الترتيب الممكن تسريعه في الاستعلامات.
  • أنواع الفهارس الأساسية:
    1. الفهرس البسيط (Single Field Index): يُبنى على حقل واحد فقط مثل { "ssn": 1 }.
    2. الفهرس المركب (Compound Index): يُبنى على حقلين أو أكثر مثل { "pnumber": 1, "pname": -1 } لتسريع استعلامات الفلترة المتعددة والترتيب.
    3. الفهرس الفريد (Unique Index): يُنشأ عبر خيار { unique: true } لفرض عدم تكرار قيمة الحقل، ويعمل كقيد فرادة (Unique Constraint) يمنع تكرار البيانات.

⚠️ مصيدة الامتحان 1: اتجاه الترتيب (1 vs -1) في الفهرس المركب

سؤال الامتحان الشهير: إذا أنشأنا فهرساً مركباً هكذا: db.sales.createIndex({ dept: 1, salary: -1 })، هل يسرع هذا الاستعلام: db.sales.find().sort({ dept: 1, salary: 1 })؟

الإجابة الحاسمة: كلا، لا يسرعه أبداً! في الفهارس الفردية يمكن السير في الاتجاهين، لكن في الفهارس المركبة يجب أن يتطابق نمط الاستعلام مع نمط الفهرس تماماً (كلاهما 1, -1) أو معكوسه التام (-1, 1). أما النمط الهجين 1, 1 فهو غير موجود في شجرة الفهرس ويسبب Collection Scan في الذاكرة.

⚠️ مصيدة الامتحان 2: قاعدة بادئة الفهرس (Index Prefix Rule)

إذا كان لديك فهرس مركب على 3 حقول: { A: 1, B: 1, C: 1 }:

  • استعلام يبحث بـ { A: 5 } ➔ يسرعه الفهرس بنجاح (لأنه البادئة).
  • استعلام يبحث بـ { A: 5, B: 10 } ➔ يسرعه الفهرس بنجاح.
  • استعلام يبحث بـ { B: 10 } أو { C: 20 } بمفردهما ➔ يعجز الفهرس عن تسريعه إطلاقاً، لأن الشجرة مبنية بترتيب الحقل الأول، والبحث بدون الحقل الأول يجبر المحرك على فحص خطي.
⚠️ مصيدة الامتحان 3: فرض الفرادة { unique: true } على كولكشن يحتوي تكرارات مسبقة

إذا كان الكولكشن يحتوي بالفعل على موظفين يحملان نفس رقم ssn: 100، ثم أصدر المطور أمراً بإنشاء فهرس فريد: db.employees.createIndex({ ssn: 1 }, { unique: true }):

ماذا يفعل النظام؟ سيفشل الأمر فوراً ويُرجع خطأ Duplicate Key، ولن يتم إنشاء الفهرس، ولن يحذف السيرفر أي مستند تلقائياً. والحل هو تطهير البيانات من التكرارات يدوياً قبل إنشاء الفهرس الفريد.

⚠️ مصيدة الامتحان 4: استحالة حذف فهرس المعرف الأساسي (_id_)

محاولة تنفيذ الأمر db.collection.dropIndex("_id_") ستقابل برفض قاطع من خادم MongoDB، وتطلق رسالة خطأ cannot drop _id index؛ لأن معمارية MongoDB تعتمد كلياً على هذا الفهرس لتأكيد فرادة المستندات والوصول اللحظي.

المحاضرة الخامسة

عمليات الحذف، الاسترجاع والإسقاط، وخط أنابيب التجميع (Aggregation Pipeline)

أوامر الحذف، قواعد الإسقاط الصارمة (Projection)، مراحل التجميع $match و $group و $sort، ودوال الإحصاء.
1
الشرح النظري والمفاهيم الهندسية الأساسية الموسعة

تتناول هذه المحاضرة الختامية أهم العمليات المتقدمة في MongoDB: حذف البيانات، القواعد الدقيقة للاسترجاع وتخصيص الحقول المعروضة (Projection)، دوال التحكم في مخرجات المؤشر (Cursor Methods)، وأخيراً معمارية خط أنابيب التجميع (Aggregation Pipeline) لمعالجة وتحليل البيانات الإحصائية المعقدة.

1. عمليات الحذف (Delete Operations):

توفر MongoDB طريقتين لحذف المستندات:

  • deleteOne(filter): يقوم بالبحث عن المستندات المطابقة للفلتر، ويحذف أول مستند فقط يعثر عليه في الترتيب الفيزيائي على القرص.
  • deleteMany(filter): يحذف كافة المستندات التي تطابق الشرط المحدد دفعة واحدة.
  • تفريغ الكولكشن بالكامل: تنفيذ db.collection.deleteMany({}) بفراغ شرطي (Empty Filter) يؤدي إلى حذف جميع المستندات مع الإبقاء على الكولكشن نفسه وفهارسه المعرفة مسبقاً (بخلاف drop() الذي يمسح الكولكشن بالكامل وفهارسه).

2. الاسترجاع والفرق بين find و findOne:

  • find(query, projection): يرجع مؤشراً (Cursor) يمكن تكرار قراءته وربطه بسلسلة من الدوال الإضافية مثل .sort() و .limit().
  • findOne(query, projection): يرجع كائناً مفرداً مباشراً (Single Document Object) لأول مستند مطابق أو null إن لم يجد شيئاً، ولا يقبل ربط دوال الـ Cursor إطلاقاً.
⚖️ القاعدة الذهبية الصارمة في الإسقاط (Projection Golden Rule)

الإسقاط (Projection) هو الوسيط الثاني الممرر لدالة find(query, projection)، ويحدد أي الحقول تُرسل عبر الشبكة وأيها تُحجب:

  • نمط التضمين (Inclusion Mode): تحديد 1 أمام الحقول المراد ظهورها. بمجرد تفعيل هذا النمط، يقوم المحرك تلقائياً بحجب كافة الحقول الأخرى.
  • نمط الاستبعاد (Exclusion Mode): تحديد 0 أمام الحقول المراد إخفاؤها. بمجرد تفعيله، يقوم المحرك تلقائياً بإظهار كافة الحقول الأخرى.
  • الحظر التام: ممنوع تماماً الجمع بين 1 و 0 للحقول العادية في نفس كائن الإسقاط! (يؤدي لرمي استثناء فوري Cannot do exclusion of field in inclusion projection).
  • الاستثناء الوحيد المنصوص عليه في المعمارية: الحقل _id يظهر دائماً وافتراضياً في النمطين، ويجوز استثنائياً كتابة { _id: 0 } لإخفائه في نمط التضمين (Inclusion) مثل: { _id: 0, fname: 1, salary: 1 }.

3. دوال السلسلة المتتابعة للمؤشر (Cursor Chaining Methods):

  • .limit(N): تحديد أقصى عدد من المستندات المعادة للمستخدم.
  • .sort({ field: 1, field2: -1 }): ترتيب النتائج المسترجعة. القيمة 1 تعني ترتيباً تصاعدياً (Ascending)، والقيمة -1 تعني ترتيباً تنازلياً (Descending).
  • .count(): عد المستندات المطابقة للاستعلام.

4. معمارية خط أنابيب التجميع (Aggregation Pipeline):

خط أنابيب التجميع هو إطار عمل هندسي فائق القوة في MongoDB؛ حيث تمر البيانات في مصفوفة من المراحل المتسلسلة (Pipeline Stages):

  • مرحلة الفلترة $match: تشبه فلتر find، وتستخدم لتقليص المستندات قبل إدخالها في المراحل اللاحقة.
  • مرحلة التجميع $group: تقوم بتجميع المستندات بناءً على مفتاح محدد في الحقل _id:
    • _id: null: يعني دمج كافة المستندات في مجموعة واحدة لحساب إحصائية عامة للمؤسسة بأكملها.
    • _id: "$dno": تجميع المستندات في مجموعات منفصلة لكل قسم. (علامة $ إلزامية للإشارة إلى مسار الحقل Field Path).
  • دوال التجميع التراكمية (Accumulators): $avg (المتوسط الحسابي)، $sum (المجموع أو العد)، $max (القيمة العظمى)، $min (القيمة الصغرى).
  • مرحلة الترتيب $sort: ترتيب مجموعات النتائج النهائية (مثلاً: { $sort: { _id: 1 } } لترتيب الأقسام تصاعدياً برقم القسم).

📝 الأسئلة المقالية النموذجية للمحاضرة الخامسة

Essay Question 1: Explain the concepts of Inclusion and Exclusion in MongoDB projection parameter, and what is the only exception?
📝 س1 مقالي: وضح بالتفصيل مفهومي الإدماج (Inclusion) والاستبعاد (Exclusion) في بارامتر الإسقاط (Projection) لدالة find؟ وما هو الاستثناء الوحيد؟

الإجابة النموذجية وتعليل الدكتور:

  • الإدماج (Inclusion): وضع القيمة 1 أمام الحقول المطلوب ظهورها فقط؛ مما يجعل النظام يُخفي تلقائياً كافة الحقول الأخرى في المستند.
  • الاستبعاد (Exclusion): وضع القيمة 0 أمام الحقول المطلوب حجبها فقط؛ مما يجعل النظام يُظهر تلقائياً كافة الحقول الأخرى في المستند.
  • الجمع بينهما: ممنوع تماماً ويؤدي لحدوث خطأ نحوي (Syntax Error)؛ لأن النظام لا يستطيع تحديد النمط الافتراضي.
  • الاستثناء الحصري: الحقل _id يظهر افتراضياً في جميع الحالات، ويجوز كتابة { _id: 0 } لإخفائه تزامناً مع استخدام 1 لباقي الحقول.
Essay Question 2: What is the Aggregation Pipeline, and why is the sequential ordering of stages ($match before $group) strictly critical?
📝 س2 مقالي: ما هو خط أنابيب التجميع (Aggregation Pipeline)؟ ولماذا يُعد ترتيب المراحل (مثل $match و $group) في غاية الخطورة والأهمية؟

الإجابة النموذجية وتعليل الدكتور:

هو سلسلة متتابعة من المراحل؛ حيث تُمرر مخرجات كل مرحلة لتكون مدخلات للمرحلة التي تليها.

أهمية الترتيب الحرج: لا بد من وضع مرحلة التصفية $match أولاً ثم التجميع $group ثانياً. التعليل: لو وضع المطور $group أولاً (لحساب متوسط الرواتب مثلاً)، ستنتج وثيقة جديدة لا تحتوي إلا على الحقول المُعرفة داخل الـ Group (مثل _id و avgSalary)، وعندما تأتي مرحلة $match بعدها لتبحث عن حقل الموظف الأصلي (مثل dno: 7)، فلن تجده إطلاقاً وستُرجع النتيجة صفر مستندات (فارغة) دون أن يُظهر النظام خطأً برمجياً!

استعلام 4 / Query 4
خط أنابيب التجميع الإحصائي العام والتصفية المسبقة (Global Aggregation & $match)
حساب الإحصائيات الشاملة على مستوى الكولكشن بالكامل بواسطة _id: null، ودمج مرحلة الفلترة $match قبل مرحلة التجميع $group.
التجميع الإحصائي العام
JavaScript / MongoDB Shell 
db.employees.aggregate([
  {
    $group: {
      _id: null,
      avgSalary: { $avg: "$salary" },
      maxSalary: { $max: "$salary" },
      minSalary: { $min: "$salary" },
      totalSalary: { $sum: "$salary" }
    }
  }
]);

db.employees.aggregate([
  {
    $match: { dno: 7 }
  },
  {
    $group: {
      _id: null,
      avgSalary: { $avg: "$salary" }
    }
  }
]);

الشرح البرمجي والتعليل:

  • الأمر الأول: يدمج كل موظفي الشركة (لأن _id: null) ويحسب المتوسط، الأعلى، الأدنى، وإجمالي الرواتب معاً في وثيقة واحدة.
  • الأمر الثاني: مرحلة $match تفلتر موظفي القسم 7 أولاً، ثم تسلم النتائج إلى $group لحساب متوسط رواتب موظفي القسم 7 فقط.
استعلام 5 / Query 5
التجميع المقسم حسب الحقول مع الترتيب النهائي (Group by Field & $sort)
تقسيم المستندات إلى مجموعات مستقلة بناءً على قيمة حقل (مثل رقم القسم "$dno") وحساب إجمالي رواتب كل مجموعة، ثم ترتيب النتائج الناتجة.
التجميع المبوب والترتيب
JavaScript / MongoDB Shell 
db.employees.aggregate([
  {
    $group: {
      _id: "$dno",
      totalSalary: { $sum: "$salary" }
    }
  },
  {
    $sort: { _id: 1 }
  }
]);

الشرح البرمجي والتعليل:

  • _id: "$dno": علامة $ تدل على استخراج قيمة الحقل dno لكل مستند وجعلها مفتاحاً للمجموعة.
  • $sort: { _id: 1 }: ملاحظة بالغة الأهمية: في الوثيقة الناتجة من $group، أصبح رقم القسم مخزناً داخل المفتاح _id؛ لذلك نرتب باستخدام _id: 1 لفرز الأقسام تصاعدياً!

⚡ مصائد وأفخاخ الامتحانات الدقيقة (Exam Traps)

⚠️ مصيدة الامتحان 1: خلط التضمين والاستبعاد في البروجكشن (Projection Trap)

سؤال الامتحان الشهير: يطلب الدكتور تحديد أي استعلام يرمي خطأ استثناء (Exception)، ويضع بين الخيارات:

db.employees.find(
  { dno: 8 },
  { fname: 1, salary: 0 }
);

الخطأ القاتل: هذا الاستعلام يرمي خطأ فادحاً في سيرفر MongoDB؛ لأن محرك العرض يعجز عن معرفة ما إذا كان النمط المطلوب هو إظهار حقول محددة فقط أم استبعاد حقول معينة! الاستثناء الوحيد المنصوص عليه هو _id: 0 مع حقول مضمنة 1.

⚠️ مصيدة الامتحان 2: نسيان علامة $ في معرف التجميع "$field"

عند الرغبة في التجميع حسب القسم، يكتب الطالب خطأً:

// كود خاطئ يدمج كل المستندات في مجموعة واحدة:
{ $group: { _id: "dno" } }

// الكود الصحيح الذي يقسم المستندات حسب قيمة القسم:
{ $group: { _id: "$dno" } }

الكارثة البرمجية: في مراحل Aggregation، أي نص بدون علامة $ يعتبره الخادم قيمة نصية ثابتة (String Literal)! فبدلاً من تقسيم الموظفين إلى أقسام (10, 20, 30)، يقوم بدمج جميع موظفي الشركة في مجموعة واحدة تحمل اسماً حرفياً "dno"! علامة $ إلزامية لدلالة استخراج مسار الحقل (Field Path Expression).

⚠️ مصيدة الامتحان 3: وضع مرحلة $group قبل $match في خط الأنابيب

سؤال الدكتور الهندسي: "لماذا يُعد كتابة [$group, $match] تصميماً هندسياً كارثياً، ولماذا يرجع صفراً؟"

db.employees.aggregate([
  { $group: { _id: null, avgSalary: { $avg: "$salary" } } },
  { $match: { dno: 5 } } // كارثة: حقل dno تم محوه في مرحلة group السابقة!
]);

الجواب النموذجي: لأن مرحلة $group أخرجت وثيقة جديدة لا تحتوي إلا على _id و avgSalary، وعندما تأتي $match لتبحث عن حقل dno، فلن تجده مطلقاً في الوثيقة الناتجة، فترجع النتيجة 0 مستندات (فارغة)! فضلاً عن أن وضع $group أولاً يجبر الخادم على قراءة ملايين المستندات بدلاً من فلترتها مسبقاً.
